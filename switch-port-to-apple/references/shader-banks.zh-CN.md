# 着色器包（`BNSH`）与 `c1` 跳转表

前面几页都默认着色器已经是 `dmsh_xlate` 能直接吃的形态：每个程序一块，`0x50` 字节 SPH +
Maxwell 指令。但基于任天堂自家 `nn::gfx` 的游戏不是这样——它们发的是**着色器包**（`BNSH`），
一个文件里塞着很多个 NVN 程序，外加这些程序运行时要读的常量数据。

本页讲容器这一侧：怎么把程序切出来，以及怎么把翻译链唯一"推不出来、又必须要"的那块数据
——`c1` **间接跳转表**——喂进去。数据取自一个真实的 `nn::gfx` 作品（88 个包、4,298 个程序）；
下面的数字只当量级参照，不要当假设。

可运行版本：`scripts/bnsh.py`（切程序）、`scripts/c1_extract.py` / `scripts/c1_verify.py`
（跳转表）、`scripts/dmsh_jobs.py`（作业文件）、`scripts/shader_chain.py`（SPIR-V → metallib）。

## `BNSH` 布局

```
0x00  "BNSH"
0x04  u32   版本（实测 0）
0x08  u32   0x0002010c
0x0c  u32   0x000cfeff
0x10  u32   "_STR" 里第一个字符串的偏移   ⇒ _STR 起点 = 这个值 − 0x1a
0x14  u32   0x00600000
0x18  u32   "_RLT" 偏移
0x1c  u32   文件大小
0x20..0x5f  全 0
0x60  "grsc"（图形着色器集合）

      grsc+0x04 / +0x0c   u64  _STR 偏移 − 0x60
      grsc+0x18           u32  变体槽数（含空槽）
      grsc+0x1c           u32  实际变体数
      grsc+0x20           u32  0xc0
      grsc+0x28           u64  变体表偏移

      变体表        每项 0x40 字节
                    +0x08  u64  控制段偏移
                    +0x10  u64  代码段偏移
      控制段池      每条以魔数 0x98761234 开头
                    小包：固定 0x9a0 字节 = 0x120 头 + 0x880 载荷
                    大库（"standard"）：尺寸可变，表布局也不同
      代码段池      每条以魔数 0x12345678 开头
      "_STR"        变体/阶段名（"default"、"imgui" …）
      "_RLT"        链接/重定位表
```

注意：控制段那 `0x880` 载荷**不是** `c1` 数据。它装的是每个变体的管线状态（blend/depth/raster），
属于回放层要的东西，不是翻译器要的东西。

### 把程序切出来

```
0x00..0x2f   NVN 头（魔数 0x12345678；其余字节实测全 0）
0x30..0x7f   SPH（0x50 字节）
0x80..       Maxwell 指令 —— 每 4 个 8 字节字一组，第 1 个是调度控制字
```

- 翻译器要的是 **SPH + 指令**，所以从 `+0x30` 导出到代码段末尾。这和 D2R 的
  `dmsh_dryrun.py`（先 `b[0x38:ci]` 再 `[0x30:]`）以及 Ryujinx 写死的 `HeaderSize = 0x50`
  是同一个约定。
- **本页其余偏移都相对这个导出文件**（SPH 在 `0x00`，指令在 `0x50`）；在包里再加 `0x30`。
- **阶段** = SPH 第 0 字 bits 10..13：`1=vs 2=tcs 3=tes 4=gs 5=ps`。
- 扫描代码段要用 `_STR` 兜上界：`header[0x10] − 0x1a`。**不要**用 `buf.find(b"_STR")`——
  在宿主映像（嵌着一个包的那种大 blob）里它会命中别处的数据。
- 只裁掉末尾**全 0 的 8 字节字**。代码段是按固定步长补齐的，而**非 0 的尾巴是有意义的**
  ——那就是 `c1` 表和/或 uniform 常量，下一节讲。

## `c1`：BRX 间接跳转表

`switch` 编译出来是 `BRX`（寄存器间接跳转）加一张放在常量段 1 里的跳转表。拿不到表，翻译器
就解不出跳转目标：它读到全 0，所有 case 都落到基址，控制流里那一片 case 体**静默丢失**
——不报错，只是走错分支（最坏情况是死循环）。

**约定**（从翻译链内置的 Ryujinx 源码里读出来的，不要自己重推）：

| 位置 | 事实 |
|---|---|
| `Decoders/Decoder.cs` `FindBrxTargetRange` | BRX 前必须是 `IMNMX.U32 Rx,Rx,UpperBound,PT` → `SHL Rx,Rx,2` → `LDC Rx,c[1][Rx+BaseOffset]`；**条数 = UpperBound + 1**，**表基址 = LDC 的 `CbufOffset`** |
| `Decoders/Decoder.cs` `FindBrxTargets` | `target = base + c1[BaseOffset + i*4]`；`base` 来自 BRX 的 `GetAbsoluteAddress()` |
| `Decoders/InstOp.cs` `GetAbsoluteAddress` | `base = address + (((int)(RawOpCode >> 20) << 8) >> 8) + 8` —— C# 的 32 位移位算术，**不是**看着像的 12 位符号扩展 |
| 解码主循环 | 地址单位是**字节**，每条指令 +8，且是 0 起算（0 = 第一条指令 = 文件偏移 `0x50`） |

实测 **1,739 个 BRX 站点，`base` 全是 0**。编译器把那个立即数字段编成恰好抵消指令地址，所以 `c1`
里的每个字都是**代码区里的绝对地址**；在导出文件里，目标就是 `0x50 + 字`。这也解释了为什么每条
都非 0、8 对齐、且小于表起点。不要去手推那个字段——把 `base` 当 0，用下面的落点校验逐个程序验证。

这里有两个容易混的偏移：

- **`CbufOffset`**（来自 `LDC`）说的是表在 **c1 缓冲里的位置**：给 blob 前面补这么多零字节。
- **加到每个表字上的目标基址**是 0（实测），也就是说表字本身就是代码地址。

### 表在哪

**在代码段的最末尾，紧接指令区之后。** 不在控制段里，也不是"控制段前 0x100 字节"
——那条 D2R 时代的规则是 D2R 自己容器的巧合，换到 `BNSH` 就不成立了。

```
[0x00,0x50) SPH      [0x50,T) 指令区
[T,R)       c1 表（可多张，首尾相接，一个 BRX 站点一张）
[R,末尾)    其它常量（uniform 默认值 —— 0x3f555556、0x4000 …）
```

三条性质让它不用猜就能定位：

1. **`T` 是一段合规 run 的起点**。`T` 前一个字不是合法表项（0、浮点数、或不是 8 对齐）。
2. **`(T − 0x50) % 16 == 0`**。指令区是整数个 4 字组。
3. **`T % 32 == 16`**（843/843 张表事后验证）。组从 `0x50` 起、32 字节一组，所以指令区结束
   必然落在这个同余类上。如果你的 `T` 算出 8 或 0，说明偏了 8 字节。

两个真花过时间的坑：

- **不要找"任意 16 对齐、后面 N 个字看着像表"的位置。** 一张长表（多个站点首尾相接）里这种
  位置一大把、相隔 4 条；从末尾往回搜会挑到**run 中间**，于是每个 case 静默错位 4~5 条。
  要取 **run 的起点**，不要取 run 里的某个位置。
- **不要假设表顶到代码段末尾。** 后面还跟着常量，而且它们长得很像表项：`0x4000` 就是 8 对齐、
  又小，孤零零地跟在一个浮点数后面。把 run 的末尾当**上界**，然后只从 `T` 起保留 `count * 4`
  字节。这不是纸上谈兵——参考作品里 843 张表中有 10 张的 run 末尾就多吞了一个 `0x4000`，
  留着它会让落点校验挂掉。

给定条数（见下面"两遍收敛"）的最小提取器。可运行版本是 `scripts/c1_extract.py`——同一个算法，
外加 note 解析、按基址补零和 `--junk-out` 对照模式；下面是核心部分：

```python
def conf(v):                      # 像不像一个表项
    return v != 0 and v % 8 == 0 and v < 0x8000

def find_table(buf, need):
    """buf = 导出的代码文件（SPH 在最前）；need = 该程序要读的条数。"""
    words = [int.from_bytes(buf[i:i+4], 'little') for i in range(0, len(buf), 4)]
    i = len(words) - 1
    while i >= 0:
        while i >= 0 and not conf(words[i]): i -= 1
        if i < 0: return None
        end = i + 1
        j = i
        while j >= 0 and conf(words[j]): j -= 1
        start = j + 1
        if (start * 4 - 0x50) % 16 == 0 and end - start >= need:
            return start * 4, end * 4      # T, R
        i = j
    return None
```

（如果表可能以 0 开头——`default` 分支落到 `base`——就允许往左吞掉紧邻的 0，只要起点仍满足
16 字节同余。这个作品里没有一张表这样。）

`find_table` 返回的是 run，不是表的长度。拼 blob 时只从 `T` 起保留 `count * 4` 字节——run 可能
把后面的常量也吞进来。

### 白拿 `base` 和 `count`

不需要写 Maxwell 解码器就能知道每个站点读了什么。先**不喂** `c1` 跑一遍翻译器：它的 accessor 会把
每次越界读记成 `c1 读越界 +OFF`，note 里就有你要的两个数：

- `count = (max(OFF) − min(OFF)) / 4 + 1`
- `base   = min(OFF)`

这个 `base` 是 `LDC` 的 `CbufOffset`——**表在 c1 缓冲里的位置**，不是上面那个目标基址（那是 0）。
表必须放在你回填的 blob 的这个偏移上：

```python
job["c1"] = (b"\0" * base + table_bytes).hex()
```

### 两遍收敛

1. **不喂** `c1` 翻译一遍 → 从 note 收集 `base`/`count`。
2. 抽表、喂进去、再翻译一遍。
3. 新解出的目标会暴露**更多** `BRX` 站点，它们可能读到更靠后的条目：把两轮的读偏移**并起来**
   再抽一次。这个作品的收敛情况是：第 2 遍剩 14 条越界读，第 3 遍 0 条。

### 不信任提取器的校验

四条都跑，每一条都独立于定位规则：

| 检查 | 什么情况下会挂 |
|---|---|
| 所有读偏移 < `len(c1)` | 表太短 / run 末尾取错 |
| `T % 32 == 16` | 在 run 里偏了 8 字节 |
| 每条都满足 `0x50 + 表项 ∈ [0x50, T)` | 混进了表后的常量（`0x4000`），或 run 从表中间开始 |
| 每条非 0 且 `% 8 == 0` | 混进了浮点数或填充字 |

再加一个**行为对照**，因为"shader 变大了"本身什么都证明不了：把同一批程序用**等长垃圾 `c1`**
（每条都填 `8`）再翻译一遍对比。这个作品上：

| | 843 个 c1 程序的 SPIR-V | 发生变化的程序 |
|---|---|---|
| 不喂 `c1` | 58.5 MB | — |
| 真 `c1` | **62.7 MB（+7.2%）** | **843 / 843**，最多 +44% |
| 垃圾 `c1` | 58.5 MB（+0.0%） | 19 / 843 |

真表每个程序 4~45 条（中位数 8，含该程序所有 `BRX` 站点），垃圾表只解出 1 个目标。

## 喂给翻译链

`dmsh_xlate` 本来就支持每个作业条目带 `"c1"`（hex 字符串，见 `Program.cs` 的 `Accessor`），
所以链路一行都不用改：`{key, stage, code, tex, img, attr, fout, local, debug, reduced, c1}`。
`scripts/dmsh_jobs.py` 可以为一整个目录的 `.code` 生成这个数组。
两点注意：

- **这类作品的 `debug: true` 是必须的。** 开着 AST 优化器时 43% 的程序在 `GenerateCall` 里崩
  （优化器把调用实参改成 `AstTextureOperation`，代码生成阶段强转 `AstOperand`）。
  详见 `pitfalls.md`。
- `c1` blob **只**被 `BRX` 解算消费。shader 里普通的 `c[1]` 读取是走正常常量段访问的，
  所以给一个不完整的 blob 对它们不算"错数据"——只是用不到。
